- `SHORT_BASE` und `SHORT_PUBLIC_BASE` sind `http://127.0.0.1:18794`. `SHORT_V2_PATH=/duell` ist ausdrücklich gesetzt (siehe Runbook).

**Staging-Adresse:** `http://127.0.0.1:18794/duell`, erreichbar über den Tunnel
`ssh -N -L 18794:127.0.0.1:18794 ssh.labor-setup.de` (oder `tools/staging/stage.sh tunnel`).

| Umgebung | Wert | Grund |
|---|---|---|
| Produktion | nicht setzen (Standard `/duell`) | wie welle-1 Voraussetzung 3 |
| Staging (labor-setup.de) | `SHORT_V2_PATH=/duell` mit `SHORT_BASE=SHORT_PUBLIC_BASE=http://127.0.0.1:18794` | Staging ist ein eigener Host. ## Rollback-Probe

Das laufende Image wurde als `mdi-staging-wrapper:prev` getaggt. Als „neue Version“ diente dasselbe Image mit einer
Markerdatei (`dist/version.txt`), damit beide Stände über HTTP und im Container unterscheidbar sind. Ablauf wie in der
D0-Umschaltung: `stop`, `rename` auf `-prev`, `run` neu. Danach Rollback mit genau der Runbook-Zeile
`docker stop W && docker rm W && docker rename W-prev W && docker start W`.

| Schritt | Zeit |
|---|---|
| Deploy neu (stop + rename + run bis `/duell` 200) | 1 579 ms (`/duell` 200 nach 899 ms) |
| Rollback gesamt | **11 523 ms** |
| davon `/duell` 200 nach `start` | 856 ms |
| davon `docker stop` der neuen Version | etwa 10 s: Node läuft als PID 1 ohne `--init` und reagiert nicht auf SIGTERM, also wartet `docker stop` das Timeout ab |

Nachprüfung: Image wieder `…bb71506c66df-b30dcecf35f3` PASS, Marker weg PASS, `/duell` byte-gleich wie vorher PASS,
`check` danach 18/18 PASS.

**Zeilen für Deploy und Rollback** (gelten ab #139; `--init` schadet nicht und räumt Zombie-Prozesse ab, ist aber nicht die
Behebung. `docker stop -t 2` **nicht** verwenden: ein SIGKILL während der Speicher-Flushes beim Beenden kann Daten kosten):

```sh
docker run -d --init --name W … IMAGE
node bin/deploy-check.mjs http://127.0.0.1:<port> --deadline 30      # Seite, Status UND Login-Pfad; Exit 0 = bereit
# Rollback
docker stop W && docker rm W && docker rename W-prev W && docker start W
node bin/deploy-check.mjs http://127.0.0.1:<port> --deadline 30
```

`deploy-check` ruft `/auth/me` mit einem erfundenen Sitzungscookie auf: `200 {authenticated:false}` heißt, die ganze
Login-Prüfung (DNS, TLS, Gate) läuft; `503` heißt nicht bereit. Ein Deploy ist erst fertig, wenn alle drei Prüfungen
bestehen, nicht schon, wenn `/duell` antwortet.
