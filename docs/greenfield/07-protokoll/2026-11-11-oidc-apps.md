## Entscheidungen (Kurzfassung)

- **Redirect:** unverändert. iOS Private-Use-Scheme `org.bunsenbrenner.cads:/oauth2redirect` (RFC 8252 §7.1; https-Callback
  erst mit Apple-Team/`webcredentials`), Android App Link `https://bunsenbrenner.org/app/oauth2redirect` (§7.2).
  Kein Redirect auf `demos-34a13a96…`: der Login gehört zur einen App-Anmeldung, nicht zum Wrapper.
- **Client:** kein neuer Client; `cads-mobile` bekommt eine Audience `mydailyidea-api`.
- **DPoP:** ja, nur Refresh-Token (Client-Policy, nur für `cads-mobile`), keine realmweite Rotation.
- **Wrapper:** `apple-app-site-association`/`assetlinks.json` auf dem Wrapper-Host müssen für den Login **nicht**
  geändert werden.

## Reihenfolge

Die Reihenfolge ist wichtig: Eine App mit DPoP gegen ein Keycloak **ohne** die Policy bekäme ein an den Schlüssel
gebundenes **Access**-Token (`cnf`, öffentlicher Client), das der Wrapper als Bearer ablehnt. Und eine App **ohne**
DPoP gegen ein Keycloak **mit** Policy kann sich nicht anmelden (`invalid_dpop_proof`; es gibt keine veröffentlichten
Builds, betroffen wären nur alte Testinstallationen).

0. assetlinks auf `bunsenbrenner.org` korrigieren (CADS-Tunnel, eigener PR + Deploy der Control-Plane, eigene Freigabe).
1. Keycloak: Sicherung, Audience-Mapper, Markierung, Client-Profil + Client-Policy (unten).
2. Wrapper: `DEMO_OIDC_*` setzen, neu starten (ssh-united.becke.biz, eigene Freigabe; kein core).
3. Apps aus PR #240 bauen und auf Testgeräten prüfen.

## Schritt 1 – Keycloak (core, nach Vorwarnung und Freigabe)

Alles mit `kcadm.sh` im laufenden Container, Admin-Login interaktiv (Passwort wird abgefragt, nicht in die Shell-Historie).

```bash
KC=$(docker ps --format '{{.Names}}' | grep -m1 keycloak)          # Containername prüfen, nicht raten
K="docker exec -i $KC /opt/keycloak/bin/kcadm.sh"
docker exec -it $KC /opt/keycloak/bin/kcadm.sh config credentials --server http://localhost:8080 --realm master --user admin
CID=$($K get clients -r ct-demo -q clientId=cads-mobile --fields id --format csv --noquotes)
test -n "$CID" || { echo "cads-mobile fehlt"; exit 1; }
B=~/kc-backup-oidc-apps-$(date -u +%Y%m%dT%H%MZ); mkdir -p "$B"
$K get clients/$CID -r ct-demo                    > "$B/cads-mobile.json"
$K get clients/$CID/protocol-mappers/models -r ct-demo > "$B/cads-mobile-mappers.json"
$K get client-policies/profiles -r ct-demo        > "$B/profiles.json"
$K get client-policies/policies -r ct-demo        > "$B/policies.json"
```

### 1a – Audience-Mapper (Access-Token bekommt `aud: mydailyidea-api`)

```bash
$K create clients/$CID/protocol-mappers/models -r ct-demo -f - <<'JSON'
{"name":"audience-mydailyidea-api","protocol":"openid-connect","protocolMapper":"oidc-audience-mapper",
 "config":{"included.custom.audience":"mydailyidea-api","access.token.claim":"true","id.token.claim":"false",
           "introspection.token.claim":"true","lightweight.claim":"false"}}
JSON
```

Fügt nur einen Eintrag zu `aud` hinzu. Die Control-Plane (`/me/installations`) prüft `aud` nur mit `CT_OIDC_ACCESS_AUD`
und erwartet dann ihren eigenen Wert; ein zusätzlicher Eintrag stört dort nicht.

### 1b – Markierung am Client (Bedingung der Policy)

```bash
$K update clients/$CID -r ct-demo -s 'attributes."mdi.dpop.refresh-only"=true'
```

Am Client **nicht** „Require DPoP bound tokens“ einschalten: dann würde Keycloak auch das Access-Token binden
(und `allow-only-refresh-token-binding` ignorieren), der Wrapper lehnt solche Tokens ab (`reason: bound` im Log).

### 1c – Client-Profil und Client-Policy (DPoP nur für das Refresh-Token)

Bestehende Profile/Policies werden **ergänzt**, nicht ersetzt (PUT ersetzt die ganze Liste):

```bash
cat > "$B/add-profile.json" <<'JSON'
{"name":"mdi-dpop-refresh","description":"cads-mobile: Refresh-Token per DPoP an den Geraeteschluessel gebunden (RFC 9449 §5, RFC 9700 §2.2.2)",
 "executors":[{"executor":"dpop-bind-enforcer","configuration":{"auto-configure":"false","enforce-authorization-code-binding-to-dpop":"false","allow-only-refresh-token-binding":"true"}}]}
JSON
cat > "$B/add-policy.json" <<'JSON'
{"name":"mdi-dpop-refresh","description":"Nur Clients mit Attribut mdi.dpop.refresh-only=true (heute: cads-mobile)","enabled":true,
 "conditions":[{"condition":"client-attributes","configuration":{"attributes":"[{\"key\":\"mdi.dpop.refresh-only\",\"value\":\"true\"}]"}}],
 "profiles":["mdi-dpop-refresh"]}
JSON
python3 -I - "$B" <<'PY'
import json, sys, pathlib
b = pathlib.Path(sys.argv[1])
pr = json.loads((b/'profiles.json').read_text()); po = json.loads((b/'policies.json').read_text())
pr.setdefault('profiles', []); po.setdefault('policies', [])
assert not any(p['name'] == 'mdi-dpop-refresh' for p in pr['profiles'] + po['policies']), 'gibt es schon'
pr['profiles'].append(json.loads((b/'add-profile.json').read_text()))
po['policies'].append(json.loads((b/'add-policy.json').read_text()))
pr.pop('globalProfiles', None); po.pop('globalPolicies', None)   # globale (eingebaute) werden nicht mitgeschickt
(b/'profiles.new.json').write_text(json.dumps(pr)); (b/'policies.new.json').write_text(json.dumps(po))
PY
$K update client-policies/profiles -r ct-demo -f - < "$B/profiles.new.json"
$K update client-policies/policies -r ct-demo -f - < "$B/policies.new.json"
```

Im Admin-Konsole prüfen (Realm settings → Client policies): Policy `mdi-dpop-refresh` aktiv, Bedingung
`client-attributes` zeigt genau die Zeile `mdi.dpop.refresh-only = true`. Andere Policies unverändert.

DEMO_OIDC_CLIENT_IDS=cads-mobile

## Rückweg

| Was | Rückgängig | Wirkung |
|---|---|---|
| Wrapper | `DEMO_OIDC_*` leeren, Container neu starten | Bearer wird ignoriert; Web unverändert; Apps sehen „anonym“ |
| Policy | in `policies.json` die Policy `mdi-dpop-refresh` auf `"enabled": false` setzen und `update client-policies/policies` – oder die Sicherung zurückspielen: `$K update client-policies/policies -r ct-demo -f - < "$B/policies.json"` | Keine Bindung mehr erzwungen; schon gebundene Refresh-Tokens verlangen weiter den Beweis (die Apps senden ihn immer) |
| Profil | `$K update client-policies/profiles -r ct-demo -f - < "$B/profiles.json"` | – |
| Mapper | `MID=$($K get clients/$CID/protocol-mappers/models -r ct-demo -q name=audience-mydailyidea-api --fields id --format csv --noquotes); $K delete clients/$CID/protocol-mappers/models/$MID -r ct-demo` | Tokens ohne `aud: mydailyidea-api`; Wrapper lehnt ab (`reason: aud`) |
| Markierung | `$K update clients/$CID -r ct-demo -f - < "$B/cads-mobile.json"` (Sicherung) | Policy greift nicht mehr |

Reihenfolge beim Rückweg: Wrapper zuerst, dann Policy, dann Mapper/Markierung. Nichts davon braucht einen Neustart
von Keycloak.

## Restrisiken

- Android-Login kommt erst nach Schritt 0 in die App zurück (assetlinks).
- `cads-mobile` steht nicht im Realm-Export von CADS-Tunnel; eine Neuanlage des Realms aus dem Export verlöre ihn.
  Folgepunkt: Client (ohne Geheimnisse, er hat keine) in `ct-demo-realm.json` aufnehmen.
- Ein Token mit `aud: mydailyidea-api` ist (bei abgeschalteter `CT_OIDC_ACCESS_AUD`-Prüfung) auch an der Control-Plane
  gültig – beides sind eigene Dienste, dieselbe App; Folgepunkt: dort `aud` prüfen.
- Kein DPoP-Nonce, kein `dpop_jkt`; beides bei Bedarf nachrüstbar.
