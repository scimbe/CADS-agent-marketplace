## Entscheidungen (Kurzfassung)

- **Redirect:** unverändert. iOS Private-Use-Scheme `org.bunsenbrenner.cads:/oauth2redirect` (RFC 8252 §7.1; https-Callback
  erst mit Apple-Team/`webcredentials`), Android App Link `https://bunsenbrenner.org/app/oauth2redirect` (§7.2).
  Kein Redirect auf `demos-34a13a96…`: der Login gehört zur einen App-Anmeldung, nicht zum Wrapper.
- **Client:** kein neuer Client. **Ein Access-Token je Resource-Server:** zwei optionale Client-Scopes an
  `cads-mobile` – `ct-api` (Audience `ct-api`, Control-Plane) und `mdi-api` (Audience `mydailyidea-api`, Wrapper).
  Die App fordert beide bei der Anmeldung an und holt danach per Refresh mit `scope=openid ct-api` bzw.
  `scope=openid mdi-api` je ein eingeengtes Access-Token; Keycloak verkleinert dabei nur das Access-Token, das
  Refresh-Token behält den Umfang (Keycloak 26.7.3 `AbstractRefreshTokenProvider`). RFC 8707 Resource Indicators sind
  in 26.7.3 nur `EXPERIMENTAL` (`Profile.Feature.RESOURCE_INDICATORS`) und binden genau eine Ressource je Grant (ein
  Refresh mit anderer `resource` ergibt `invalid_target`) – daher nicht genutzt. Die Control-Plane verlangt für
  `cads-mobile` `aud: ct-api` (`CT_OIDC_CLIENT_AUD`, Standard an), der Wrapper `aud: mydailyidea-api`: ein an einer
  Stelle abgegriffenes Token gilt an der anderen nicht.
- **DPoP:** ja, nur Refresh-Token (Client-Policy, nur für `cads-mobile`), keine realmweite Rotation.
- **Wrapper:** `apple-app-site-association`/`assetlinks.json` auf dem Wrapper-Host müssen für den Login **nicht**
  geändert werden.

## Reihenfolge

Die Reihenfolge ist wichtig:
- Eine App mit DPoP gegen ein Keycloak **ohne** die Policy bekäme ein an den Schlüssel gebundenes **Access**-Token
  (`cnf`, öffentlicher Client), das der Wrapper als Bearer ablehnt.
- Eine App **ohne** DPoP gegen ein Keycloak **mit** Policy kann sich nicht anmelden (`invalid_dpop_proof`). Es gibt
  keine veröffentlichten Builds; betroffen wären nur alte Testinstallationen.
- Die Control-Plane mit #899 verlangt für `cads-mobile` `aud: ct-api`. Deshalb müssen die Scopes in Keycloak **vor**
  dem Deploy von #899 stehen, sonst kann die App `/me/installations` nicht mehr nutzen.

```bash
#  erwartet: trustEmail=false bei JEDEM IdP
$K get "authentication/flows/first%20broker%20login/executions" -r ct-demo --fields providerId,requirement,displayName
#  erwartet: KEIN providerId "idp-auto-link"; "idp-review-profile"/"idp-create-user-if-unique"/"idp-confirm-link" +
#  "idp-email-verification" oder "idp-username-password-form" (Verknüpfung nur nach Bestätigung)
$K get authentication/required-actions -r ct-demo --fields alias,enabled | grep -E 'VERIFY_EMAIL|UPDATE_EMAIL'
#  erwartet: VERIFY_EMAIL enabled; eine E-Mail-Änderung nur über UPDATE_EMAIL mit Bestätigung der neuen Adresse
```

**Bekannter Ist-Stand laut Realm-Export:** `haw-gitlab` hat `trustEmail: true`. Die Vorbedingung ist damit **nicht
erfüllt**. Mögliche Wege: `trustEmail` dort abschalten (ändert Keycloak, eigene Freigabe; HAW-Nutzer bestätigen ihre
Adresse dann einmal) oder bewusst akzeptieren, weil die Subjekt-Bindung eine spätere Übernahme ohnehin abweist. Die
Entscheidung trifft der Nutzer, sie wird hier nicht getroffen. Die anderen IdPs (google, github, gitlab) stehen im
Export auf `false`; live prüfen.

### 1a – Client-Scopes je Resource-Server (`ct-api`, `mdi-api`), optional an `cads-mobile`

```bash
$K get client-scopes -r ct-demo --fields name > "$B/client-scopes.json"
for S in ct-api:ct-api mdi-api:mydailyidea-api; do
  NAME=${S%%:*}; AUD=${S#*:}
  $K create client-scopes -r ct-demo -f - <<JSON
{"name":"$NAME","protocol":"openid-connect","description":"Access-Token nur fuer $AUD (cads-mobile, ein Token je Resource-Server)",
 "attributes":{"include.in.token.scope":"true","display.on.consent.screen":"false"},
 "protocolMappers":[{"name":"audience-$AUD","protocol":"openid-connect","protocolMapper":"oidc-audience-mapper",
   "config":{"included.custom.audience":"$AUD","access.token.claim":"true","id.token.claim":"false","introspection.token.claim":"true","lightweight.claim":"false"}}]}
JSON
  SID=$($K get client-scopes -r ct-demo -q name=$NAME --fields id --format csv --noquotes | head -1)   # Ergebnis prüfen: genau dieser Scope
  $K update clients/$CID/optional-client-scopes/$SID -r ct-demo
done
```

Keine Audience mehr direkt am Client (kein Client-Mapper): sonst trüge jedes Token beide Audiences. Prüfen, dass
`cads-mobile` keinen Audience-Mapper aus einem früheren Versuch hat (`$K get clients/$CID/protocol-mappers/models`).

### 1b – Markierung am Client (Bedingung der Policy)

```bash
$K update clients/$CID -r ct-demo -s 'attributes."mdi.dpop.refresh-only"=true'
```

Am Client **nicht** „Require DPoP bound tokens“ einschalten: dann würde Keycloak auch das Access-Token binden
(und `allow-only-refresh-token-binding` ignorieren), der Wrapper lehnt solche Tokens ab (`reason: bound` im Log).

### 1c – Client-Profil und Client-Policy (DPoP nur für das Refresh-Token)

Bestehende Profile/Policies werden **ergänzt**, nicht ersetzt (PUT ersetzt die ganze Liste):

```bash
cat > "$B/add-profile.json" <<'JSON'
{"name":"mdi-dpop-refresh","description":"cads-mobile: Refresh-Token per DPoP an den Geraeteschluessel gebunden (RFC 9449 §5, RFC 9700 §2.2.2)",
 "executors":[{"executor":"dpop-bind-enforcer","configuration":{"auto-configure":"false","enforce-authorization-code-binding-to-dpop":"false","allow-only-refresh-token-binding":"true"}}]}
JSON
cat > "$B/add-policy.json" <<'JSON'
{"name":"mdi-dpop-refresh","description":"Nur Clients mit Attribut mdi.dpop.refresh-only=true (heute: cads-mobile)","enabled":true,
 "conditions":[{"condition":"client-attributes","configuration":{"attributes":"[{\"key\":\"mdi.dpop.refresh-only\",\"value\":\"true\"}]"}}],
 "profiles":["mdi-dpop-refresh"]}
JSON
python3 -I - "$B" <<'PY'
import json, sys, pathlib
b = pathlib.Path(sys.argv[1])
pr = json.loads((b/'profiles.json').read_text()); po = json.loads((b/'policies.json').read_text())
pr.setdefault('profiles', []); po.setdefault('policies', [])
assert not any(p['name'] == 'mdi-dpop-refresh' for p in pr['profiles'] + po['policies']), 'gibt es schon'
pr['profiles'].append(json.loads((b/'add-profile.json').read_text()))
po['policies'].append(json.loads((b/'add-policy.json').read_text()))
pr.pop('globalProfiles', None); po.pop('globalPolicies', None)   # globale (eingebaute) werden nicht mitgeschickt
(b/'profiles.new.json').write_text(json.dumps(pr)); (b/'policies.new.json').write_text(json.dumps(po))
PY
$K update client-policies/profiles -r ct-demo -f - < "$B/profiles.new.json"
$K update client-policies/policies -r ct-demo -f - < "$B/policies.new.json"
```

Im Admin-Konsole prüfen (Realm settings → Client policies): Policy `mdi-dpop-refresh` aktiv, Bedingung
`client-attributes` zeigt genau die Zeile `mdi.dpop.refresh-only = true`. Andere Policies unverändert.

## Schritt 2 – Wrapper (ssh-united.becke.biz, Container 127.0.0.1:8794; kein core)

Logs: `auth-bearer-refused` mit `reason` (höchstens einmal pro Minute und Grund; u. a. `aud`, `lifetime`,
`subject-changed`), `auth-run` mit `via: "bearer"`; nie Token oder E-Mail.

**Betriebshinweis (L4):** Ist die App-Anmeldung an, entscheidet ein `Authorization`-Header allein. Setzt etwas vor dem
Wrapper (Proxy, Monitoring, ein künftiger Edge-Filter) einen eigenen `Authorization`-Header (Basic oder Bearer),
gilt ein Browser mit gültigem Gate-Cookie als **nicht angemeldet**. Heute setzt der Pfad Edge → Agent → Wrapper keinen
solchen Header; bei jeder Änderung dort prüfen.

**Subjekt-Bindung (M2):** Wird ein Keycloak-Konto bewusst neu angelegt (neues `sub`, gleiche Adresse), weist der Wrapper
es ab (`subject-changed`), bis der Eintrag entfernt ist. Schlüssel des Eintrags: siehe Wrapper-README („Subjekt-Bindung“).

## Rückweg

| Was | Rückgängig | Wirkung |
|---|---|---|
| Wrapper | `DEMO_OIDC_*` leeren, Container neu starten | Bearer wird ignoriert; Web unverändert; Apps sehen „anonym“ |
| Policy | in `policies.json` die Policy `mdi-dpop-refresh` auf `"enabled": false` setzen und `update client-policies/policies` – oder die Sicherung zurückspielen: `$K update client-policies/policies -r ct-demo -f - < "$B/policies.json"` | Keine Bindung mehr erzwungen; schon gebundene Refresh-Tokens verlangen weiter den Beweis (die Apps senden ihn immer) |
| Profil | `$K update client-policies/profiles -r ct-demo -f - < "$B/profiles.json"` | – |
| Scopes | je Scope `$K delete clients/$CID/optional-client-scopes/$SID -r ct-demo`, dann `$K delete client-scopes/$SID -r ct-demo` | App-Anmeldung scheitert (`invalid_scope`); vorher Control-Plane `CT_OIDC_CLIENT_AUD=off` setzen oder #899 zurücknehmen |
| Control-Plane #899 | `CT_OIDC_CLIENT_AUD=off`, neu starten | `/me/*` prüft für `cads-mobile` keine Audience mehr (alter Stand) |
| Markierung | `$K update clients/$CID -r ct-demo -f - < "$B/cads-mobile.json"` (Sicherung) | Policy greift nicht mehr |

Reihenfolge beim Rückweg: Wrapper zuerst, dann Control-Plane (`CT_OIDC_CLIENT_AUD=off`), dann Policy, dann
Scopes/Markierung. Nichts davon braucht einen Neustart von Keycloak.

## Restrisiken

- Android-Login kommt erst nach Schritt 0 in die App zurück (assetlinks).
- `cads-mobile` steht nicht im Realm-Export von CADS-Tunnel; eine Neuanlage des Realms aus dem Export verlöre ihn.
  Folgepunkt: Client (ohne Geheimnisse, er hat keine) in `ct-demo-realm.json` aufnehmen.
- Kein DPoP-Nonce, kein `dpop_jkt`; beides bei Bedarf nachrüstbar.
- **L7 – iOS-Redirect per Private-Use-Scheme** (`org.bunsenbrenner.cads:/oauth2redirect`): eine andere App kann
  dasselbe Scheme registrieren. PKCE S256 mit 64-Byte-Verifier und die `state`-Prüfung machen einen abgefangenen Code
  wertlos; `ASWebAuthenticationSession` liefert den Callback an die aufrufende Sitzung. Upgrade-Pfad: ab iOS 17.4
  `ASWebAuthenticationSession.Callback.https(host:path:)` mit Universal Link, sobald ein Apple-Team und Associated
  Domains (`webcredentials:bunsenbrenner.org`, AASA mit `webcredentials`) bestehen; dann den https-Redirect am Client
  ergänzen und das Scheme entfernen.
- Ein in Keycloak widerrufenes Access-Token gilt am Wrapper bis zu seinem Ablauf (höchstens 5 min, Cache ≤ 60 s).
- `haw-gitlab` mit `trustEmail: true` (siehe Schritt V), bis entschieden.
